# InvisibleWaterMark

**Invisible watermarking for photos, with cryptographic proof of authorship.**
Everything runs on your own machine. Photos and private keys never leave it.

This tool does **not** prevent theft. It traces theft and proves who made the photo.
Everything it cannot do is listed under [Limitations](#limitations).

Full documentation, and the application itself, are in Korean —
see [한국어 문서](#한국어) below.

### Three layers, three jobs

| Layer | Where | Survives | Proves |
|---|---|---|---|
| **Author tag** (48 bit) | DWT level 2, sparse | recompression, crop, denoise, **being overwritten** | points at your public key |
| **Message** | DWT level 1 | the ordinary upload path | nothing on its own |
| **Sidecar** (`.sig.json`) | separate file | (not in the image) | Ed25519 signature — undeniable |

Two design choices carry most of the weight:

- **Resize to the platform's size first, then embed.** Embed first and the platform's own
  resize drops detection to chance level.
- **Sparse, key-derived placement.** Each public key claims 48 of 192 grid cells. When
  someone re-watermarks your photo their cells mostly miss yours, so your tag survives
  (41–44 of 48 bits, reproduced across 6 random key pairs).

### Headline numbers

Instagram 1080px, bits recovered out of 48. The right column is the quality of the
*attacked photo itself*: an attack strong enough to strip the mark wrecks the photo too.

| Attack | Result | Attacked photo |
|---|---|---|
| Upload recompression | 48/48 | 39 dB |
| Screenshot | 48/48 | 38 dB |
| Downscale to 50% | 48/48 | 39 dB |
| Crop 10% off the edges | 48/48 | 30 dB |
| Crop to centre 40% | **lost** (43/48) | 16 dB |
| Denoising | 45/48 | 38 dB |
| Brightness / contrast | 48/48 | 18 dB |
| Someone overwrites it | 41–44/48 | — |
| Crop **and** colour grading | **lost** (41/48) | 15.7 dB |
| Generative regeneration (img2img) | **lost** | — |

Embedding costs 46–47 dB PSNR (SSIM 0.96–0.998), which is not perceptible.

### Two ways to run it

- **Web app** — open the deployed site. Everything happens inside the browser tab and
  nothing is uploaded. A photo watermarked in the browser reads back in the desktop app
  at 48/48 bits, and its signature verifies there.
- **Desktop** — clone and run locally. See [실행](#실행).

### Limitations

- Cannot stop anyone from taking the photo. It only helps afterwards.
- Cannot block AI training. It writes the IPTC/PLUS `DataMining` opt-out, but that has no
  enforcement, and social networks strip metadata on upload.
- Does not survive generative regeneration (img2img) — shared by every invisible
  watermark today.
- Cropping combined with colour grading can slip through.
- A targeted attacker who knows your public key and edits the code can erase the mark.
- Does not prove who was *first*. Signature timestamps are self-reported.
- **Automatic face detection is not reliable.** Three detectors are merged, finding 22 of
  24 faces on a hard test set where a single pass found 19. Check the preview before
  posting and paint over anything missed.

# 한국어

사진에 눈에 보이지 않는 워터마크를 심고, Ed25519 서명으로 원작자를 증명하는 도구다.
계산은 전부 이 컴퓨터 안에서 끝난다. 사진도 개인키도 밖으로 나가지 않는다.

**도용을 막아주지는 못한다. 도용을 추적하고 원작자를 증명할 뿐이다.**
못 하는 일은 [알려진 한계](#알려진-한계)에 빠짐없이 적어두었다.

## 실행

파인더에서 `실행.command` 를 더블클릭하면 된다.

처음 한 번은 필요한 부품을 내려받느라 1~2분 걸린다(인터넷 필요). 그다음부터는 바로 열린다.
준비가 끝나면 브라우저가 `http://127.0.0.1:8765` 을 자동으로 연다. 이미 켜져 있을 때는
서버를 새로 띄우지 않고 브라우저만 연다.

끌 때는 그 창을 닫거나 Control-C 를 누른다. 10분 동안 쓰지 않으면 알아서 꺼진다.

터미널에서 직접 띄우려면:

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/python server.py     # → http://127.0.0.1:8765
```

첫 화면에서 "내 도장"을 한 번 만들어야 한다. 방식은 셋 중 하나를 고른다.

- **암호 걸고 만들기**(권장) — 암호를 두 번 입력받는다
- **암호 없이 만들기** — 파일 권한 0600 으로만 지킨다
- **필요 없어요** — 증명을 포기하고 문장만 심는 [간단 모드](#키-없이-쓰기-간단-모드)로 넘어간다

개인키는 `~/.watermark/key.pem` 에 저장된다.
**꼭 백업해두자. 잃어버리면 그동안 심어둔 워터마크를 하나도 증명하지 못한다.**

## 구조: 세 겹으로 나눠 심는다

| | 작성자 태그 | 문장 | 사이드카 `.sig.json` |
|---|---|---|---|
| 어디에 | 이미지 안 (DWT 레벨 2) | 이미지 안 (DWT 레벨 1) | 별도 파일 |
| 무엇을 | `SHA256(공개키)` 앞 48비트 | 원하는 문장 | 해시·문장·지각해시에 대한 서명 |
| 견디는 것 | 재압축, 크롭, 디노이즈, 색보정, 덮어쓰기 | SNS 업로드 경로까지 | (이미지와 무관) |
| 증명력 | 이 공개키를 가리킨다 | 없다 | 부인할 수 없다 |

공개키 자체가 신원 등록부 노릇을 한다. 프로필이나 깃허브에 올려두면 누구나 대조할 수 있어서
따로 데이터베이스를 둘 필요가 없다. 48비트짜리 태그에 512비트 서명을 넣을 수는 없으니,
확실한 증명은 사이드카가 맡는다.

## 설계 1. 플랫폼 규격으로 줄인 다음에 심는다

워터마크는 리사이즈에 약하다. 3000px 사진에 그대로 심어서 인스타그램에 올리면 1080px 로
깎이는 과정에서 검출률이 찍기 수준까지 떨어진다. 그래서 올릴 해상도로 먼저 줄이고,
그다음에 심는다. 플랫폼이 더 건드릴 게 없으니 워터마크가 그대로 살아남는다.

## 설계 2. 거친 구조에 싣는다

디노이즈든 블러든 리사이즈든, 워터마크를 지우려는 시도는 대체로 고주파부터 건드린다.
그래서 반대로 DWT 레벨 2, 즉 이미지의 거친 뼈대에 싣는다. 이쪽을 지우려 들면 사진의
형태 자체가 무너진다.

## 설계 3. 띄엄띄엄 심어 덮어쓰기를 견딘다

양자화(QIM)는 나중에 쓴 값이 이긴다. 모든 블록에 빽빽하게 심어두면 남이 덮어쓰는 순간
전부 잃는다.

그래서 12x16, 192칸짜리 격자에서 공개키가 고른 48칸에만 심는다. 키가 다르면 고르는 칸도
달라지고(평균 12~15칸만 겹친다), 남이 덮어써도 겹치지 않은 칸에 내 비트가 남는다.

## 측정 결과

### 공격별 검출 (Instagram 1080x720, 48비트 중 일치 비트)

| 공격 | 결과 | 공격당한 사진 화질 |
|---|---|---|
| 업로드 재압축 | 48/48 검출 | 39.0dB |
| 강한 재압축 (q60) | 48/48 검출 | 36.2dB |
| 스크린샷 캡처 | 48/48 검출 | 38.4dB |
| 저장 후 50% 축소 | 48/48 검출 | 38.8dB |
| 가장자리 10% 크롭 | 48/48 검출 | 29.5dB |
| 정중앙 40%만 남김 | **43/48 소실** | 16.3dB |
| 노이즈 제거 | 45/48 검출 | 37.6dB |
| 노이즈 제거 + 강한 재압축 | 46/48 검출 | 36.9dB |
| 12%까지 줄였다 되돌림 | 47/48 검출 | 38.2dB |
| 밝기·대비 조작 | 48/48 검출 | 18.2dB |
| 크롭 + 밝기·대비 | **41/48 소실** | 15.7dB |

지각 마스킹(격자 제거)을 켠 상태에서 잰 값이다. 마스킹을 켜기 전에는 정중앙 크롭도
48/48 로 살아남았다. 그 생존성을 내주고 매끈한 배경의 격자 얼룩을 없앤 셈이다.

오른쪽 dB 는 공격당한 사진 자체의 화질이다. 워터마크를 지울 만큼 세게 건드리면 사진도
함께 망가진다. 이 도구가 기댈 수 있는 보장은 사실상 이것 하나뿐이다.

### 덮어쓰기 생존

| | 원작자 태그 | 도용자 태그 | 읽히는 문장 |
|---|---|---|---|
| 원작자가 보호 | 48/48 | — | "원작자 홍길동…" |
| 도용자가 그 위에 다시 보호 | **41~44/48 검출** | 48/48 | "도용자 mallory…" |

두 태그가 나란히 남는다. 무작위 키 6쌍으로 6번 모두 재현했고, 브라우저 화면에서 처음부터
끝까지 해봐도 같았다(도용본에서 원작자 태그 43/48, 우연히 맞을 확률은 7,300만분의 1).
빽빽하게 심던 이전 설계에서는 같은 자리에서 47/48 이 33/48 로 무너졌다.

### 화질

| 구성 | PSNR |
|---|---|
| 태그만 | 47.2dB |
| 태그 + 문장 | 45.9dB |
| 키 없이 문장만 | 49.2dB |

SSIM 은 0.96~0.998 이다. 32px 블록이 만드는 격자 얼룩은 지각 마스킹을 끄면 매끈한 영역에
그대로 드러난다. 켜면 매끈한 영역의 픽셀 변화가 평균도 최대도 0 이 되면서 격자도 사라진다.

### 지각 마스킹, 격자를 없앤 대가

마스킹이 없으면 하늘이나 벽처럼 매끈한 곳에 격자가 눈에 띈다. QIM 이 블록마다 값을
격자점으로 끌어다 놓는데, 평평한 블록에는 그 흔적을 가려줄 무늬가 없기 때문이다.
그래서 AC 에너지가 양자화 간격의 `MASK_K = 0.5` 에 못 미치는 블록은 건너뛴다. 다만
사진 전체가 평평한 경우까지 신호가 사라지면 곤란하니 바닥값(`MASK_FLOOR`)을 뒀다.

그라디언트 시험 이미지에서 매끈한 영역의 최대 픽셀 변화가 9 에서 0 으로 떨어졌다.
이 중 마스킹이 줄인 몫은 6 에서 0 까지고(해당 영역 PSNR 43.4 → 46.1dB), 9 에서 6 까지는
같은 작업에 함께 들어간 별개의 수정이 줄였다. 양자화 격자점 아무 데나가 아니라 가장
가까운 점으로 옮기도록 고친 것이다.

대가도 있다. 사진 한 장 기준으로 11가지 공격 중 실패가 1개에서 2개로 늘었다. 정중앙
크롭과 크롭+밝기·대비 조작에서 워터마크를 잃는다(마스킹 전에는 뒤쪽만 실패했다).
수치를 보고 일부러 고른 맞바꿈이다. 평범한 사진에서 티가 안 나는 쪽이, 저 두 가지
편집을 견디는 쪽보다 중요하다고 봤다.

`MASK_K` 를 0.35, 0.50, 0.65, 0.85 로 훑어보니 0.35~0.65 는 결과가 똑같았다. 평평한
블록은 AC 에너지가 거의 0 이라 어느 문턱을 쓰든 똑같이 걸러진다. 반대로 0.85 는 무늬가
있는 블록까지 파고들어 같은 사진에서 실패가 2개가 아니라 4개로 늘었다. 그래서 결과가
같은 구간의 한가운데인 0.5 를 골랐다.

## 문장 심기 (선택)

48비트 태그에는 문장이 들어가지 않는다. 한글 한 문장이면 700비트가 넘는다. 그래서 문장은
DWT 레벨 1 이라는 별도의 층에 심는다. 블록이 4배 촘촘해 용량은 넉넉하지만 그만큼 약하다.

| 이미지 | 용량 | 한글 |
|---|---|---|
| 1080x720 (인스타 가로) | 88바이트 | 29자 |
| 1080x1350 (인스타 세로) | 171바이트 | 57자 |
| 2048x1365 (X) | 334바이트 | 111자 |

| | 문장 | 작성자 태그 |
|---|---|---|
| 업로드 재압축 · 스크린샷 · 50% 축소 | 그대로 | 검출 |
| 강한 재압축 · 크롭 · 밝기·대비 | 깨짐 | 검출 |

정리하면, 올리고 내려받는 평범한 경로에서는 문장이 읽히고, 편집을 당하면 문장은 잃어도
태그는 남는다.

문장은 CRC 검사를 통과해 정확히 복원됐을 때만 보여준다. 한 비트만 틀려도 글자가 깨지는데,
깨진 글자를 진짜로 착각하면 곤란하니 아예 띄우지 않는다. 문장은 사이드카 서명이 덮으므로
이미지 속 문장이 깨져도 원래 문구는 증명할 수 있다.

두 층은 서로 간섭한다. 반드시 태그를 먼저 심고 문장을 나중에 심는다. 순서를 바꾸면 거친
층에 쓰는 동안 미세 층 계수가 흔들려 768비트 중 230비트가 깨졌다. 문장층 강도도 36이
아니라 24로 뒀다. 36이면 문장은 더 질겨지지만 태그의 크롭 복구가 무너진다.

## 키 없이 쓰기 (간단 모드)

증명까지는 필요 없고 "이 사진은 내 것"이라는 문장만 남기고 싶다면 키 없이도 쓸 수 있다.
[보호하기] 탭에서 **"키 없이 문장만 심기"** 를 체크한다.

| | 키 있음 | 키 없음 |
|---|---|---|
| 심는 것 | 태그 + 문장 | 문장만 |
| 사이드카 | 서명된 `.sig.json` | **없음** |
| 원작자 증명 | 암호학적으로 가능 | **불가능** |
| 화질 | 39.9dB | **45.8dB** |

무엇을 포기하는지는 알고 써야 한다. 서명이 없으면 남이 똑같은 문장을 자기 사진에 심어도
가려낼 방법이 없고, 그 사람이 자기 사진이라고 우겨도 반박할 근거가 없다.

검증할 때도 키가 필요 없다. [검증하기] 탭에 사진만 넣으면 심긴 문장을 읽어준다.

## AI 학습 거부 선언

파일에 IPTC/PLUS 표준의 데이터 마이닝 거부 표시를 넣는다(기본으로 켜져 있다).

```
plus:DataMining = http://ns.useplus.org/ldf/vocab/DMI-PROHIBITED-AIMLTRAINING
```

IPTC Photo Metadata 2023.1 이 PLUS 어휘를 받아들여 표준으로 삼은 항목이고, ExifTool 은
12.67 부터 지원한다. JPEG 의 XMP(APP1) 세그먼트에 쓰며 418바이트가 늘어난다. Pillow 로
다시 읽어 네임스페이스까지 맞는지 확인했다. 사이드카 서명이 이 선언까지 덮으므로 나중에
"그런 적 없다"고 발뺌할 수 없다.

한계도 같이 봐야 한다.

- **강제력이 없다.** 크롤러가 읽고 지켜줘야 의미가 생기는 의사 표시이지, 기술적 차단이 아니다.
- **SNS 를 거치면 사라진다.** 인스타그램과 X 는 업로드할 때 메타데이터를 지운다. 포트폴리오,
  메일, 직접 다운로드처럼 파일을 그대로 건네는 경로에서만 살아남는다.

### 왜 워터마크가 아니라 메타데이터에 넣나

크롤러가 들여다보는 곳은 파일 메타데이터이지 이 워터마크가 아니다. 워터마크에 넣으면 SNS 는
통과하겠지만 아무도 읽지 않는다. 읽히는 자리에 쓰는 편이 낫다.

### 이미지를 망가뜨려 학습을 막는 방법은 넣지 않았다

확산 모델 인코더를 겨냥한 적대적 섭동(PhotoGuard 계열)은 리사이즈와 JPEG 재압축에 가장 먼저
죽는다. 그런데 이 도구는 플랫폼 규격으로 먼저 줄이고, SNS 가 또 재압축한다. 워터마크를
살리려고 짜놓은 구조가 그 섭동을 스스로 지우는 셈이다. PyTorch 와 수 GB 짜리 모델 가중치도
필요해서 "전부 이 컴퓨터 안에서"라는 성질까지 깨진다. 효과가 없을 것을 알면서 넣으면
보호받고 있다는 착각만 남는다.

## 얼굴 가리기

함께 찍힌 다른 사람의 초상권을 지키는 기능이다. 사진에서 얼굴을 찾아 번호를 붙이고,
사용자가 고른 얼굴만 워터마크와 지각 해시보다 먼저 되돌릴 수 없게 지운다.

가리는 방식은 두 가지다.

**단색**(기본)은 그 영역의 채널별 중앙값 색을 16단계로 양자화해 채우고, 화소마다 아주 작은
난수를 더한다. 출력이 원본 얼굴에 의존하는 통로는 양자화된 색 세 개뿐이라 복원할 정보
자체가 남지 않는다. 알고리즘이 튼튼해서가 아니라 남은 정보량이 없어서이므로 증명이 가능하다.

**모자이크**는 그 모양을 원하는 사람을 위한 선택지일 뿐 보호 수단이 아니다. 블록 평균에는
원본이 준 정보가 그대로 남고, 그 위에 얹는 지터는 이 사실을 바꾸지 못한다.
후보 200장 중 진짜 원본을 맞히게 해서 재식별률을 쟀다(우연히 맞을 확률은 0.5%).

| 가리기 방식 | 재식별 top-1 | 남는 표본 |
|---|---|---|
| 단색 (기본) | 2.0% | 3개 |
| 모자이크, 블록4/지터12 (모자이크 기본값) | 100.0% | 48개 |
| 모자이크, 블록4/지터24 | 100.0% | 48개 |
| 모자이크, 블록4/지터48 | 74.5% | 48개 |
| 모자이크, 블록4/지터96 | 13.5% | 48개 |
| 모자이크, 블록3/지터12 | 100.0% | 27개 |
| 모자이크, 블록3/지터24 | 82.5% | 27개 |
| 모자이크, 블록3/지터48 | 25.5% | 27개 |
| 모자이크, 블록3/지터96 | 6.0% | 27개 |
| 모자이크, 블록2/지터12 | 45.5% | 12개 |
| 모자이크, 블록2/지터24 | 17.5% | 12개 |
| 모자이크, 블록2/지터48 | 5.5% | 12개 |
| 모자이크, 블록2/지터96 | 1.0% | 12개 |

단색이 우연보다 조금 높게 나오는 이유는 분명하다. 양자화한 중앙값 색을 설계상 그대로
남기기 때문이다. 일부러 열어둔 유일한 통로인데, 이것만으로 얼굴을 되살리기에는 턱없이
모자란다. 반면 모자이크는 보통의 모자이크로 보이는 설정 전부에서 공격자가 사실상 매번
정확한 원본을 찾아낸다. **초상권을 정말로 지켜야 한다면 단색을 쓰자. 모자이크는 모양만
가릴 뿐이다.**

자동 탐지를 최종 결과로 여기면 안 된다. 찾아낸 얼굴은 기본으로 전부 체크되고, 사진 위를
끌어서 박스를 직접 더하거나 지울 수 있다. 옆얼굴, 작은 얼굴, 가려진 얼굴은 탐지가 곧잘
놓치기 때문에 손으로 칠하는 기능을 보조가 아니라 기본 수단으로 뒀다.

## 메타데이터 지우기

같은 화면에 체크박스가 하나 있다. **"워터마크 없이 위치·시각·기종 정보(EXIF)만 지우기."**
키도 문장도 필요 없다. 증명할 게 없으니 사진을 넣으면 정리된 사진이 나올 뿐이다.

워터마크를 심을 때도 재인코딩의 부산물로 EXIF 가 이미 전부 사라진다. 다만 그동안은 그
부산물만 얻으려 해도 워터마크의 키와 문장 요구를 함께 받아들여야 했다. 이 체크박스는 그
요구를 떼어낸 것이다.

사진을 디코드해 캔버스에 다시 그리고 재인코딩한다. `protect()` 가 쓰는 경로와 같아서 GPS
좌표, 촬영 시각, 기종이 같은 이유로 사라진다. 방향(Orientation) 정보도 먼저 픽셀에 구워
넣으니 세로 사진이 옆으로 눕지 않는다. 얼굴 가리기와 AI 학습 거부 선언도 이 모드에서 그대로
쓸 수 있다. 둘 다 워터마크에 기대는 기능이 아니기 때문이다.

## 변형을 되돌리는 3단계

어떤 변형을 당했느냐에 따라 되돌리는 방법이 다르다. 그래서 싼 것부터 차례로 넓혀 가고,
앞 단계에서 확실해지면 거기서 멈춘다.

1. **그대로 읽기** — 리사이즈됐다면 원래 크기로 되돌린 것도 함께 본다 (후보 2개)
2. **밝기·대비 되돌리기** — 이득과 오프셋 후보 40가지 (후보 80개)
3. **크롭 정렬 전수 탐색** — 그 40가지마다 픽셀 오프셋과 격자 시프트를 전부 (후보 200만개)

3단계가 그나마 빠른 이유가 있다. 픽셀 오프셋이 4 만큼 차이 나면 DWT 계수도 그만큼 밀린
것과 같다. 그래서 DWT 는 4가지만 계산해두고 나머지는 계수를 잘라 재사용한다
(DWT 4가지 x 4x4 블록 x 시프트 192가지).

| 상황 | 소요 |
|---|---|
| 그대로 읽힘 | 0.0초 |
| 크롭 50%, 탐색으로 찾음 | 0.9초 |
| 워터마크 없음, 예산 소진 | 13.6초 |

찾으면 바로 멈추니 문제는 못 찾을 때다. 그래서 2·3단계를 합쳐 12초라는 벽시계 예산을 뒀다.
예산이 없으면 몇 분씩 붙들고 있었다.

### 비트 수가 아니라 확률로 판정한다

후보를 많이 볼수록 우연히 들어맞을 확률도 올라간다. 그래서 "지금까지 본 후보 수"를 반영한
오탐 확률로 판정하고, 기준은 1e-4 이하로 뒀다. 화면에도 실제 확률을 함께 띄운다.

| 단계 | 후보 수 | 필요한 일치 |
|---|---|---|
| 1단계 | 2 | 39/48 |
| 2단계 | 80 | 41/48 |
| 3단계 | 200만 | 46/48 |

페이로드를 48비트로 잡은 이유가 여기 있다. 32비트였다면 3단계에서 32비트를 전부 맞혀도
기준을 못 넘어서 크롭 탐색 자체가 성립하지 않는다. 여유가 생긴 덕에 색보정이 섞인 크롭까지
잡아낸다.

## 덮어쓰기에 대한 3중 방어

남이 이 사진에 자기 워터마크를 다시 심는 공격(ambiguity attack)은 비가시 워터마크 전반의
알려진 약점이다. 세 겹으로 대응한다.

### 1. 띄엄띄엄 심어서 살아남는다

위 [덮어쓰기 생존](#덮어쓰기-생존) 참조. 41~44/48 로 검출된다.

**왜 레벨 2인가.** 이전 설계인 레벨 3 빽빽한 배치는 블록이 726개뿐이라 띄엄띄엄 나눌 여유가
없었다. 레벨 2는 3015개라 4분의 1만 써도 비트당 표본이 15개 남는다.

**레벨 3 빽빽 + 레벨 2 띄엄띄엄을 겹쳐도 봤지만 실패했다.** 남이 레벨 3 에 쓰면 레벨 2
전체가 흔들려 생존층이 20/48 로 무너졌다. 거친 층에 쓰면 그 아래가 통째로 흔들리기
때문이다. 그걸 버틸 만큼 생존층 강도를 올리면 이번에는 내 레벨 3 태그가 30/48 로 무너졌다.
두 층이 서로를 죽이니 하나만 골라야 했다. 강도는 180이 최적이었고, 160과 200 은 무작위 키
6개 중 1~2개에서 생존에 실패했다.

### 2. 지각 해시로 파생 관계를 보인다

워터마크는 덮어쓸 수 있어도 사진 자체는 지우지 못한다. 그래서 사이드카에 원본의 지각
해시(사진의 생김새를 63비트로 요약한 값)를 함께 서명해 둔다.

| 대상 | 거리 (63비트 중) | 판정 |
|---|---|---|
| 덮어쓴 도용본 · 재압축 · 축소 · 밝기조작 | 2~6 | 같은 사진 |
| 가장자리 10% 크롭 | 16 | 편집된 같은 사진 |
| 정중앙 50% 크롭 | 26 | 판정 불가 |
| 무관한 사진 20종 | 22~40 | 다른 사진 |

닮았다는 사실은 증거를 보강할 뿐 확증은 아니다. 도용자도 자기가 훔친 사진의 지각 해시에
서명할 수 있어서, 이것만으로 누가 먼저인지는 가려지지 않는다. 표본이 합성 이미지라 비슷한
풍경 사진끼리는 더 가까이 나올 수 있어 기준을 보수적으로 잡았다.

### 3. 사이드카가 확정 증명을 맡는다

덮어쓴 도용자는 자기 사이드카에 "이것이 내 원본"이라고 서명한다. 그런데 그 해시가 원작자의
출력물과 바이트 단위로 같다.

```
도용자가 '내 원본'이라 서명한 해시 : e76627e1859d25cf…
원작자가 '내 보호본'이라 서명한 해시: e76627e1859d25cf…   ← 동일
원작자만 가진 진짜 원본의 해시     : 804f111088c4df9c…   ← 도용자는 못 만듦
```

원작자는 워터마크를 심기 전의 원본 파일을 갖고 있고, 그 해시가 서명돼 있다. 도용자는 그
파일을 만들어낼 수 없다. **원본 파일과 사이드카를 반드시 보관해야 하는 이유가 이것이다.**

그래서 화면에서도 안내문 한 줄로 끝내지 않는다. 보호가 끝나면 챙길 것 세 가지(보호된 이미지,
사이드카, 원본 파일)를 단계로 보여주고, 사이드카를 실제로 내려받았는지 추적한다. 안 받았으면
배지가 "아직 안 받음"으로 남고, 그 상태에서 창을 닫으려 하면 브라우저가 한 번 더 확인한다.

다만 서명의 시각은 자기 신고라서 양쪽 다 "내가 먼저"라고 주장할 수 있다. 선점을 증명하려면
OpenTimestamps 같은 외부 앵커가 필요한데, 그건 해시를 외부 서버로 보내는 일이다. 아무것도
이 컴퓨터를 벗어나지 않는다는 이 도구의 성질과 정면으로 부딪혀서 넣지 않았다.

### 덮어쓰기 차단은 실수 방지용이다

기존 워터마크가 감지되면 삽입을 거부하고, 사용자가 "그래도 덮어쓰기"를 눌러야 진행한다.
감지 경로는 둘이다. 내 워터마크는 공개키를 대조해 정확히 잡아내고, 남의 문장은 CRC 통과
여부로 잡는다(우연히 통과할 확률 2⁻³²). 남의 문장은 발견한 내용을 그대로 보여준다.

문장 없이 태그만 심은 남의 워터마크는 알아내지 못한다. 띄엄띄엄 심는 탓에 블록의 4분의 1
에만 표시가 있어서 통계로는 평범한 사진과 구별되지 않았다(칸별 통계까지 시도했지만 문서형
이미지에서 오탐이 났다). 빽빽하게 심던 시절에는 위상 쏠림으로 잡아냈으니, 띄엄띄엄 배치로
얻은 생존성과 맞바꾼 셈이다. 덮어써도 워터마크가 살아남으니 경고를 놓쳐도 피해는 작다.

이 차단은 같은 프로그램을 쓰는 상대에게만 걸린다. 도용자는 이 프로그램을 안 쓰거나 파이썬
코드 한 줄만 지우면 그만이다. **실수를 막는 장치이지 보안 통제가 아니다.**

## 보안: 데이터가 이 컴퓨터를 벗어나지 않는다

| 항목 | 확인 방법 | 결과 |
|---|---|---|
| 소스에 외부 송신 코드 | requests·urllib·socket 등 전수 검색 | 없음 |
| 화면이 부르는 주소 | fetch 호출 전수 확인 | `/api/*` 상대경로뿐 |
| 외부 리소스 (폰트·CDN) | 외부 URL 검색 | 없음 (`data:`/`blob:` 만) |
| 처리 중 실제 통신 | 사진 처리 내내 `lsof` 로 소켓 감시 | 루프백 외 연결 0건 |
| 네트워크 노출 | LAN IP 로 접속 시도 | 연결 거부 |
| 사진이 디스크에 남는지 | 업로드 중 임시파일 감시 | 없음 (메모리에서만) |
| 개인키 유출 경로 | 응답에 실리는 값 확인 | 공개키만 |

점검에서 두 가지가 실제로 걸렸고, 둘 다 고쳤다.

**1MB 넘는 업로드가 디스크 임시파일로 떨어졌다.** 웹 프레임워크(starlette)의 기본 스풀
임계값이 1MB 라 웬만한 사진은 처리 중에 시스템 임시 폴더로 기록됐다. 임계값을 업로드 상한
위로 올려 막았다.

**악성 웹사이트가 이 로컬 서버를 부릴 수 있었다.** 127.0.0.1 에 묶여 있어도 사용자가 방문한
악성 페이지가 브라우저를 통해 POST 를 보낼 수 있다(CORS 는 응답을 못 읽게 할 뿐 요청 자체는
막지 않는다). DNS 리바인딩까지 가면 읽기도 뚫린다. 사진을 보관하거나 돌려주는 엔드포인트가
없어 사진 유출은 애초에 불가능했지만, 남이 이 사용자의 개인키로 서명을 시킬 수는 있었다.
Host/Origin 검사를 넣어 막았다.

서버가 떠 있는 시간이 곧 노출 시간이다. 그래서 화면은 탭이 보이고 최근에 조작이 있을 때만
1분마다 신호를 보낸다. 탭을 닫든 자리를 비우든 신호가 끊기고, 10분 뒤 서버가 스스로 꺼진다.

남는 위험은 이렇다.

- 서버가 떠 있는 동안 같은 컴퓨터의 다른 프로그램은 `127.0.0.1:8765` 에 접근할 수 있다.
- 키 암호는 루프백 HTTP 로 평문 전송된다. 컴퓨터를 벗어나지는 않는다.
- 개인키 파일(권한 0600)을 읽을 수 있는 프로그램은 신원을 훔칠 수 있다.

## 알려진 한계

과장하지 않으려고 아는 것을 전부 적는다.

- **생성형 재생성(img2img)은 못 버틴다.** 확산 모델로 이미지를 다시 만들면 워터마크가
  사라진다. 이 도구만의 문제가 아니라 현재 나와 있는 모든 비가시 워터마크의 공통 한계다.
- **표적 덮어쓰기는 못 막는다.** 칸 선택이 공개키에서 나오므로, 내 공개키를 아는 상대가
  프로그램을 고치면 내 칸만 노릴 수 있다. 애초에 모든 칸을 덮어써도 그만이다.
- **너무 작은 조각은 못 읽는다.** 격자가 12x16 이고 블록 하나가 16px 이라 최소
  256 x 192px 은 남아 있어야 한다.
- **크롭한 뒤 리사이즈한 경우는 못 찾는다.** 정렬은 되돌려도 배율까지는 알 수 없다.
- **문장 층은 편집을 못 견딘다.** 크롭, 강한 재압축, 밝기 조작 중 하나만 겪어도 깨진다.
  용량과 강인성이 정면으로 맞바꿔지는 탓이고, 그래서 작성자 태그를 따로 둔 것이다.
- **워터마크만으로는 위조할 수 있다.** 남의 공개키 태그를 자기 사진에 심으면 그만이다.
  확정 증명은 사이드카가 맡는 이유다.
- **시각은 증명하지 못한다.** 서명에 적힌 시각은 자기 신고다.
- **AI 학습 자체를 막지는 못한다.** 추적하고 귀속시키는 도구이지 차단하는 도구가 아니다.
- **얼굴 자동 찾기는 완벽하지 않다.** 탐지기 셋을 돌려 결과를 합친다. TinyFaceDetector 를
  입력 크기 두 가지로, 그리고 SSD MobileNet v1 로 돌린다. 어려운 사진 8장(정답 24명)에서
  22명을 찾고, 한 번만 돌리던 이전 방식은 19명이었다. 여전히 못 찾는 쪽은 이마가 화면 밖으로
  잘린 얼굴이다(3명 중 1명). 여럿을 합치다 보니 오탐이 가끔 하나 생기는데 이쪽이 안전한
  방향이다. 오탐은 체크를 끄면 그만이지만, 아무도 못 찾은 얼굴은 그대로 발행되기 때문이다.
  올리기 전에 미리보기를 눈으로 확인하고 놓친 얼굴은 직접 칠하자.

  측정 (어려운 사진 8장, 정답 24명):

  | 경우 | 한 번만 | 셋을 합침 |
  |---|---|---|
  | 쉬운 정면 3명 | 3 | 3 |
  | 입·턱 가림 | 3 | 3 |
  | 이마가 잘림 | 1 | 1 |
  | 화면 끝에 반쯤 걸침 | 1 | 1 |
  | 고개 25도 기울임 | 3 | 4 (오탐 1) |
  | 멀리 있는 작은 얼굴 | **0** | **3** |
  | 어두운 사진 | 3 | 3 |
  | 쉬운 5명 | 5 | 5 |
  | **합계** | **19/24** | **22/24** |

  모델만 크게 바꿔서는 안 됐다. SSD MobileNet 하나로 갈아타도 19/24 로 같았다. 작은 얼굴에서
  이기고 어두운 사진에서 졌을 뿐이다. 결국 이긴 조합은 서로 놓치는 게 다른 셋을 합치는
  것이었다. 대신 모델이 5.6MB 늘었고, 얼굴 가리기를 처음 쓸 때만 내려받는다.

## 파일

- `dwtdctsvd.py` — DWT-DCT-SVD 알고리즘. invisible-watermark(MIT)에서 가져와 정리했다.
  옮겨온 시점에 원본과 바이트 단위로 같은 출력을 내는 것을 확인한 뒤 아래를 고쳤다.
  역 DWT 밴드 순서 버그(PSNR 33 → 43dB), uint8 랩어라운드 버그, 크롭 내성을 위한 주기 격자
  배치, 띄엄띄엄 칸 선택, 그리고 전수 탐색을 감당하게 하는 벡터화.
- `watermark.py` — 키·삽입·추출·서명·지각해시·벤치마크, 그리고 `mask_faces()` 얼굴 가리기
- `server.py` — 로컬 웹 API. 127.0.0.1 전용, Host/Origin 검사, 유휴 시 자동 종료,
  `/lib` 로 `site/` 를 한 번 더 서빙해 얼굴 탐지 JS 를 웹앱과 공유한다
- `static/index.html` — 데스크톱 UI
- `test_watermark.py` — 자체 점검. `.venv/bin/python test_watermark.py`
- `test_face_mask.py` — 얼굴 가리기 자체 점검. `.venv/bin/python test_face_mask.py`
- `실행.command` — 파인더에서 더블클릭하는 실행기. 첫 실행 때 준비까지 알아서 한다
- `site/` — 브라우저에서 도는 웹 앱(정적 파일). Vercel 같은 곳에 그대로 올린다.
  서버로 사진을 보내지 않고 계산이 전부 탭 안에서 끝나므로, 사진이 내 기기를 벗어나지
  않는다는 성질이 그대로 유지된다.
  - `wm-core.js` 수학(DWT·DCT·최대특이삼중항) · `wm.js` 워터마크·문장·지각해시
  - `app-core.js` 키·서명·보호/검증 · `app.js` 화면 · `index.html`
  - `face.js` 얼굴 탐지·가리기 · `face-ui.js` 선택 패널 (데스크톱과 공유)
  - `vendor/` face-api.js 와 모델 가중치 (출처와 해시는 `NOTICE` 참조)

## 웹 앱과 데스크톱 앱은 호환된다

같은 형식을 쓴다. 브라우저에서 심은 워터마크를 파이썬 앱이 읽고, 그 반대도 된다.
옮긴 결과가 정확한지 기계적으로 대조했다.

| 항목 | 결과 |
|---|---|
| DCT 행렬 · 4x4 DCT · Haar DWT 2단계 | 오차 1e-13 |
| 최대 특이삼중항 | 오차 3e-13 |
| 작성자 태그 · 칸 선택 | 완전 일치 |
| 태그 삽입 결과 픽셀 | 98,304개 전부 동일 |
| CRC32 · 문장 프레임 · 용량 계산 | 완전 일치 |
| 지각 해시 | 같은 파일에서 완전 일치 (구현 차이 최대 2비트, 허용 10) |
| **브라우저가 심음 → 파이썬이 읽음** | **태그 48/48 · 문장 정확 · 선언 확인** |
| **브라우저 서명 → 파이썬이 검증** | **유효** |

옮기는 과정에서 세 가지를 맞춰야 했다.

- **칸 선택을 해시 기반으로 바꿨다.** 원래 `numpy.default_rng().choice()` 를 썼는데, 난수
  알고리즘을 다른 언어에서 똑같이 재현하는 방식은 깨지기 쉽다. 지금은
  `SHA256(seed || 칸번호)` 순위로만 정한다.
- **정규 JSON 을 파이썬 쪽에 맞췄다.** 파이썬 `json.dumps` 는 비ASCII 를 `\uXXXX` 로
  escape 한다. JS 는 원문 그대로 내보내므로 두 결과를 맞추지 않으면 서명 대상 바이트가
  달라져 검증이 실패했다.
- **지각 해시의 축소를 OpenCV 와 맞췄다.** 면적 가중 평균에 정수 반올림까지 해야 한다.
  반올림을 빼먹었더니 평균 8비트가 어긋났다.
